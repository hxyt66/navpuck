# NavPuck 手机端（Android Chrome PWA）

把 PC 上的 `tools/navigator.py` 搬到手机里：手机当"导航大脑"，通过 **BLE** 连
ESP32-S3 圆屏，不需要 USB、不需要电脑、不需要任何地图 API key。

- 路线：**OSRM** 公共实例（免费、无 key）
- 街道路网：**Overpass API**（免费、无 key），localStorage 缓存 + 失败退避 +
  **记住上次成功的镜像**（sticky）；
  **抓不到时不影响导航**（状态面板会说清楚，也可以整个关掉）
- 链路：**Nordic UART Service**（设备已经实现）
- 线协议：**一个字节都没有改**，与 `tools/navpuck_proto.py` 逐字节相同

★ = 与 Python 有对应关系的移植文件。**没有构建步骤、没有 npm、没有框架**：
全部是经典 `<script>`，直接双击 `index.html` 也能打开（但 BLE 用不了，见第 3 节）。

### 自测怎么跑

```bash
cd <navpuck 根目录>
node phone/test/run-all.mjs          # 四套一起跑，任一套失败则非 0 退出
node phone/test/selftest.mjs         # 只跑字节级
node phone/test/parity.mjs           # 只跑 Python 对拍（需要 python 在 PATH 里）
node phone/test/integration.mjs      # 只跑集成
node phone/test/ui.mjs               # 只跑界面接线
```

四套各管一段，缺一不可：

| 套件 | 管什么 | 抓得到的典型问题 |
|---|---|---|
| `selftest.mjs` | 字节级 | 字段顺序、CRC、分片边界、解析器重同步 |
| `parity.mjs` | 与 `navigator.py` 的语义 | 取整方式、投影、路口下标、视野值 |
| `integration.mjs` | 接线 | 分片降档、队列丢谁、30 秒重发、看门狗、端到端闭环 |
| `ui.mjs` | `index.html` ↔ `app.js` | id 拼错、按钮没绑上、初始化崩、面板没更新 |

`parity.mjs` 在没有 Python 的机器上会打印 **SKIP** 并以 0 退出 —— 那是"没执行"，
不是"通过"。字节级一致性由 `selftest.mjs` 独立覆盖。

## 2. 怎么用（配对流程）

1. **设备上电**，确认它在广播 `NavPuck-XXXX`（`docs/ble.md`）。
2. 手机 Chrome 打开本页面（怎么打开见第 3 节，**必须先解决 HTTPS**）。
3. 按 **`连接设备`** → 在弹出的选择框里选 `NavPuck-XXXX`。
   - ⚠️ Web Bluetooth 要求**用户手势**，所以必须是按这个按钮，不能自动连。
   - 页面上 `链路` 徽章变绿 = 已连上、通知已订阅。
4. 按 **`用当前位置作起点`**（第一次会弹定位授权；拿到定位后再按一次写入起点）。
   - 室内收不到 GPS 时这一条会一直卡在"等待定位"。状态面板的 `定位` 一栏旁边
     会直接写出最后一次错误（权限被拒 / 不可用 / 超时）和"该怎么办"，
     不用去翻日志（日志默认是收起的）。
   - 完全拿不到 GPS 也能测：展开 **`高级 / 手动定位`**（见下一节）。
5. 选一个预设或填经纬度，按 **`规划并开始导航`**。
6. 设备屏幕上应该出现指引线；页面状态面板开始跳数。

**停车/收工**按 `停止`（停 10Hz 循环），再按 `断开`。

### 室内没有 GPS 时怎么测（手动 / 模拟位置）

`navigator.geolocation.watchPosition({enableHighAccuracy:true})` 在楼里基本永远
拿不到 fix —— 页面会停在"等待定位"，整条链路（BLE → 路线 → 底图 → 10Hz 更新
→ 设备显示）就都测不了。所以有一个**不依赖 GPS** 的位置源：

1. 展开 **`高级 / 手动定位`**。
2. 填**纬度 / 经度**（十进制度，例如杭州 `30.2545` / `120.1350`）和
   **航向**（度，0 = 正北，顺时针；默认 0），速度可选（只影响速度栏和 ETA）。
   ⚠️ 起点坐标**不要和目的地重合**（页面上默认填的是"湖滨路"
   `30.2500` / `120.1600`）：起终点重合会让路线长度变成 0，页面会明确报
   `路线长度为 0，没法导航`。
3. 勾 **`使用手动位置`**，或直接按 **`应用手动位置`** —— 两条路等价。
4. 此时顶部会一直显示 **`⚠️ 正在使用手动位置`** 横幅，状态面板的 `定位` 变成
   `手动定位`，并且起点自动设为这两个坐标。
5. 按 **`连接设备`** → **`规划并开始导航`**，设备上就会动起来。目的地照样可以
   选预设或直接填经纬度，全程不需要任何定位权限。
6. 想看**地图旋转**对不对（设备是"车头朝上"、机身没有磁力计），就改 `航向`
   输入框 —— 改完立刻生效，不用再按"应用"；设备上的地图与箭头会跟着转。
7. 测完取消勾选 `使用手动位置` 就切回真实 GPS。**模拟期间横幅一直在**，
   免得把一次模拟运行误当成真实定位。

⚠️ 手动位置是**静态**的：车停在那个坐标上不动，地图不会滚。它的用途是验证
"链路通不通"和"转向/旋转对不对"，不替代真实骑行验证。

### 第一次跑之前值得知道的

- **手机必须和车头同向固定**。设备没有磁力计，"相对车头方位"是手机算出来
  发给它的（`docs/roadmap.md` 里写了要加磁力计才能解决）。放口袋里时
  `rel_bearing` 没有意义 —— 界面选项里取消"手机与车头同向固定"会让箭头改用
  路线切线方向（仍然有用，只是不再是"相对车头"）。
- 勾上选项里的 **`显示日志`**。第一次真机联调基本都要看日志。
- 页面的 `已发帧` 一栏显示 `已发 / 丢弃`。**丢弃数持续增长**说明链路跟不上，
  优先看它。
- 状态面板的 **`底图`** 一栏会直说底图现在怎么样（`拉取中 1/3` / `42段/330点` /
  `42段/330点·缓存` / `不可用 · 60s后重试` / `已关闭`），下面还有一行常显的详情，
  写清楚"为什么、下一步做什么"。**底图挂了不影响导航** —— 路线、箭头、转向提示
  和 10Hz 更新照常（`integration.mjs` 第 12 节钉着这条）。

## 3. 怎么把它放到手机上跑（**这一节是整份文档最需要说实话的地方**）

### 硬约束

Web Bluetooth **只能在安全上下文（secure context）里用**
（[MDN](https://developer.mozilla.org/en-US/docs/Web/API/Web_Bluetooth_API)：
*"The Web Bluetooth API can only be used in a secure context"*）。
而 service worker / 可安装 PWA 同样要求安全上下文。

手机上的"安全上下文"只有三种：

| 方式 | 免费用？ | 手机上可行？ |
|---|---|---|
| `http://localhost` | 是 | **不行** —— 手机上的 `localhost` 是手机自己，不是你的 PC |
| **HTTPS**（真证书） | 要花钱买域名/证书 | 行 |
| `http://` + Chrome 白名单 flag | 是 | 行，但要手动改 flag（见下面 C 方案） |

**"在 PC 上起个 HTTPS 服务器给手机访问"是行不通的**，这一点必须说清楚：
自签证书在 Android Chrome 上会报 `ERR_CERT_AUTHORITY_INVALID`，**即使用户把 CA
装进系统信任库也照样被拒**（Chrome 只认自己那套根，不认用户装的私有 CA；
Espruino/Bangle.js 社区踩过同一个坑：
[1](https://github.com/orgs/espruino/discussions/1390)、
[2](https://github.com/orgs/espruino/discussions/1655)）。
所以"免费 + 简单 + 长期可用"三者**不可能同时满足**，只能按下面排序挑一个。

### A 方案（推荐，最省事、长期可用）：托管到免费的静态托管

把 `phone/` 整个目录传到一个免费 HTTPS 静态托管，用那个网址打开。

- **GitHub Pages**：免费、给 HTTPS、可以装到主屏。
  把 `phone/` 的内容放到仓库里（或 `docs/` 目录），在 Settings → Pages 打开。
  得到 `https://<用户名>.github.io/<仓库>/` 即可。
- **Cloudflare Pages / Netlify / Vercel** 同类，免费档都够用。

优点：一次配置，之后手机上存个书签/主屏图标就行；service worker 缓存下来后
**离线也能打开**（BLE 不走网络，OSRM/Overpass 只在规划和抓路网时才需要网络）。

缺点：需要一个托管账号；仓库是公开的（这几行代码没什么机密，但心里要有数）。
注意 **Overpass / OSRM 仍然需要手机有网**（骑行途中的路网刷新靠它；
已经缓存过的区域可以离线用）。

### B 方案（不想用托管、也不想改 flag）：**在 PC 上继续跑** —— 也就是维持现状

诚实的结论：如果你的目标是"彻底不要 PC"，那就必须走 A 或 C。
如果只是想在手机上调试/试用，可以用 **Android 的 USB 端口转发**把 PC 上的
`localhost` 变成手机上的 `localhost`：

```bash
adb reverse tcp:8000 tcp:8000      # 手机上的 localhost:8000 -> PC 的 8000
cd phone && python -m http.server 8000
```

然后在手机 Chrome 打开 `http://localhost:8000/`。
这是**真正的安全上下文**（loopback 例外），不需要证书、不需要改 flag。
但它**必须有 USB 连着 PC** —— 所以它只是"调试用"，不是骑车时的方案。

### C 方案（不花钱、不带 PC，但要手动改 flag）：Chrome 的 insecure-origin 白名单

Chrome 有一个逃生口：把某个 `http://` 源手动标记成"当作安全上下文"。

1. PC 上：`cd phone && python -m http.server 8000`（记下 PC 的局域网 IP，
   例如 `192.168.1.50`）。
2. 手机 Chrome 打开 `chrome://flags/#unsafely-treat-insecure-origin-as-secure`。
3. 在输入框里填 `http://192.168.1.50:8000`，把开关设成 **Enabled**，重启 Chrome。
4. 打开 `http://192.168.1.50:8000/` —— `navigator.bluetooth` 就可用。

限制（都要接受）：
- **每次骑车都得让 PC 开着并连着同一个局域网** —— 这等于没有摆脱 PC。
- 这个 flag 在部分 Chrome 版本/企业策略下会被移除或不可用。
- 改过 flag 的源**不能安装成 PWA**（可安装性检查会失败），只能当普通网页用。
- 所以严格来说 C 只适合"验证一下代码能不能跑"，不适合当最终方案。

### 结论

**想真正"不带 PC 上摩托" → 走 A 方案（免费静态托管）。**
其余两个方案都需要 PC 在场，只是用途不同（B 用于 ADB 调试，C 用于快速验证）。

### 装到主屏

在 A 方案（或 B 方案的 localhost）打开后：
Chrome 右上角 `⋮` → **`添加到主屏幕`** / **`安装应用`**。
装好后从主屏图标启动，是独立窗口（`display: standalone`），没有地址栏。

上面三种方案里只有 A 和 B 能走这一步；C 因为改了 flag 装不了。

## 4. 这个端口相对 PC 版改了什么（以及没改什么）

### 逐字照搬、**故意不改**的

| 行为 | 值 | 为什么不能"顺手优化" |
|---|---|---|
| 视野 | **固定** `ROUTE_FAR_M = 160m` | PC 版明确删掉了"接近路口自动拉近"：那个忽远忽近的观感更让人误判距离 |
| 路线原点 | **发这一窗时骑手的位置**（滑动窗口） | 原点固定在路线起点的话，点走 i16 米就只到 ±32.7km，一天 100km 的骑行根本发不出去；固定窗口又让线尾离骑手越来越远 |
| 窗口长度 / 点距 | `WINDOW_M = 10km` / `STEP_M = 10m` | 10km 只用掉 i16 米上限的 1/3；10m 点距在 160m 视野里是 16 个点，线才不像折角 |
| 重锚 | 离开原点 **5km**（半个窗口）+ 窗口末端快到而路还长 | 不重锚的话骑手会骑出画出来的线；5km 一次 ≈ 每 7 分钟 4KB |
| 重锚先发空片 | `total_points = 0`，再发新窗口 | wire 上没有 route_id，新旧窗口点数往往一样；不先清空，设备可能把两窗拼成一条不存在的路 |
| **重锚的同时重建底图** | 同一轮用**内存里那份路网**按新原点重投影 + 重发（`_resend_map()`），**不联网** | 底图和路线窗口同源（相对当前原点）。原点一挪 5km、底图不重建，设备减掉新的 `pos_east_m/pos_north_m` 后整张图就偏 5km —— 屏幕外，看着就是"底图掉了"，而它自己好起来要等下一次成功的抓取（最坏 120 秒预算）。路网数据一个字节都没变，只有原点变了，所以这是纯计算。⚠️ 覆盖不到新原点时**不发空帧**（那会把设备上那张擦成白屏），只写一行日志等下次抓取 |
| 底图 0 段 | 刷新返回 0 条路**不清空**手上那份（`ways` 原样留着，状态标"缓存已旧"） | 清了就没得画，而"这一带暂时没抓到"和"这里本来就没有路"是两件事 |
| 窗口重发 | **每 30 秒** + 链路 down→up 时（逐字节相同，不带空片） | 丢一个分片就整段没有指引线，而且设备上没有任何提示 |
| 窗口点数 | ≤ **1024**（实测 1001），点距恒定 10m | 设备端数组只有那么大；点距不匀则 `next_turn_index` 算不出来 |
| 抽稀/加密 | `_densify` 步长 25m | 不加密的话"前方 180m 的点"和"路口前后 35m 的方向"完全失真 |
| 路口识别 | 前后各 35m 比方向，>25° 才算 | 只看相邻点夹角会被 GPX 噪声带歪 |
| 底图裁剪 | 半径 260m 抓取、`view*1.6` 裁剪、7m 抽稀 | 与 `MAP_MAX_POINTS=330` / `MAP_MAX_SEGMENTS=60` 配套 |
| 缓存 | 命中就不联网；复用半径 180m | 公共 Overpass 会限流、会 504 |
| `remark` 检查 | 有 `remark` 就判失败 | **必须**：限流时它是 `HTTP 200 + elements:[] + remark`，不看就会静默拿到"0 条路" |

### 底图（Overpass）挂掉的时候（这一版补的）

公共 Overpass **真的会整体挂掉**，而且**哪一个还活着是随时间变的**。开发机上实测
（对 9 个公共实例逐个探活 `GET /api/status`，再对能用的那个发一次真的
`way[highway](around:300,...);out geom;`）：

| 实例 | 结果 |
|---|---|
| `maps.mail.ru/osm/tools/overpass` | **HTTP 200 —— 9 个里唯一能用的** |
| `overpass-api.de` / `overpass.kumi.systems` / `overpass.private.coffee` / `overpass.openstreetmap.ru` / `z.overpass-api.de` / `lz4.overpass-api.de` | `/api/status` 超时 |
| `overpass.osm.jp` | TLS 证书信任失败 |
| `overpass.osm.ch` | HTTP 400 |

`maps.mail.ru` 的真查询是 **HTTP 200 + `Access-Control-Allow-Origin: *`**（所以浏览器
**可以**直连），但**慢：一个小查询要 17.6 秒**，43.9 KB / 46 条路。
⚠️ 这些是**开发机**上的实测，**没有**在手机所处的网络、也没有在真正的浏览器里复验过。

改之前的表现是界面永远停在"等待路网" —— 用户既不知道这是上游故障，也不知道
**导航根本没受影响**。现在这层的行为（全部在 `map.js`，命令字 `MAP_*`）：

| 常量 / 行为 | 值 | 为什么 |
|---|---|---|
| `ENDPOINTS[0]` | **`maps.mail.ru`** | 实测唯一能用的排第一。上一版它排第三：两个死镜像各烧 12 秒，轮到它时 30 秒预算只剩 6 秒 —— **唯一能用的镜像被饿死**，用户看到"全部镜像失败" |
| `MAP_ENDPOINT_TIMEOUT_MS` | **45000** | 每个镜像单独超时（`AbortController` + `Promise.race` 双保险）。**17.6 秒实测值的 2.5 倍** —— 12 秒那一版 < 17.6 秒，等于注定掐断唯一能用的镜像。谁要调小，先重新实测 |
| `MAP_REFRESH_BUDGET_MS` | **120000** | 一整轮刷新的**墙钟预算** = 2 个完整切片（2×45s）+ 第三片至少 30 秒。N 个镜像里前 N-1 个哪怕各烧一整片，最后一个也拿得到 ≥ 20 秒（> 实测 17.6 秒） |
| `MAP_MIN_ENDPOINT_SLICE_MS` | **20000** | 剩余预算不够就不再开新镜像。这一片必须长得够一次真查询跑完（实测 17.6 秒），否则失败原因会写成"请求超时"，看起来像镜像的错，其实是我们的预算不够 |
| **sticky 镜像** | 成功过的排下一轮第一 | `localStorage` 的 `navpuck.osm_endpoint.v1` 记着上次成功的是谁，下一轮先试它；它要是再失败就**立刻忘掉**、退回静态顺序。静态列表永远会有一段时间是错的（实测那一刻 9 个里只有 1 个能用） |
| 镜像轮换 | 失败后从下一个开始 | 排头但长期挂掉的实例不会把后面的镜像永远饿死 |
| 退避冷却 | 60 → 120 → 240 → 480 → **600**（上限） | `MAP_FAIL_COOLDOWN_S` 起算的指数退避。服务刚恢复时最怕一群客户端同时回来把它再打死 |
| 缓存优先 | 新鲜缓存：**完全不联网**；过期缓存：**先用上**并标"缓存已旧" | 缓存键里**没有 endpoint**，所以镜像列表怎么改，手机上的旧缓存都还能用 |
| `显示街道路网底图`（复选框） | 关掉 = 一个 Overpass 请求都不发 | 省流量、省电、Overpass 挂了时不用干等。选择**记在 localStorage** 里（`navpuck.opt.map.v1`），关掉时还会给设备发一帧空 `NAV_MAP` 把已经画出来的路网清掉（设备对 `seg_count == 0` 的处理见 `src/ui/ui_puck.cpp` 的 `renderMap()`） |

⚠️ 查询本身（`way[highway](around:260,...);out geom;`）**一个字都没改**：半径必须是
`MAP_RADIUS_M`（`MAP_RADIUS_M - MAP_REFRESH_MOVE_M = 180m > ROUTE_FAR_M = 160m`，调小
就会出现空洞，而且它是和 Python 对拍的常量），而"17.6 秒 / 200 / CORS `*`"这份实测
就是**这条查询**测出来的 —— 改了形状，那份实测就不再说明任何事。

界面上的状态（`OsmMapSource.status()` → 状态面板 `底图` 一格 + 下面那行详情）：

| 状态 | 那一格 | 详情（摘要） |
|---|---|---|
| `trying` | `拉取中 2/3` | 正在请求第 2/3 个镜像 `overpass.kumi.systems`（单镜像 45 秒、整轮 120 秒）；导航不受影响 |
| `ok` | `42段/330点` | 底图正常：来自 `maps.mail.ru`，42 段 / 330 点（本次实时抓取） |
| `cached` | `42段/330点·缓存` | 底图来自本地缓存（抓取于 3 分钟前）；本次没有联网 |
| `stale` | `42段/330点·缓存已旧` | 数据偏旧（抓取于 9 天前），正在后台尝试刷新；导航不受影响 |
| `unavailable` | `不可用 · 60s后重试` | **底图服务（Overpass）暂时无响应，不影响导航，路线和箭头照常工作。** 后面接逐镜像的原因（`overpass-api.de：请求超时（45 秒）；…`）和退避说明 |
| `disabled` | `已关闭` | 已关闭：不再向 Overpass 发任何请求；不影响导航，勾选可重新打开 |
| `idle` | `未开始拉取` | 只在导航刚启动、还没发出第一次请求的那 0.5 秒里出现 |

⚠️ 上一版那三句话里含糊的"等待路网…"**只在 `idle` 这半秒里出现**；一旦问过
Overpass 就一定有明确结论（成功、来自缓存、还是不可用 + 原因）。

`refresh()` 永远不抛异常（异常也会变成一条状态 + 一条 `[map]` 日志），
`app.js` 里底图那一整块还额外包了 `try/catch` —— 底图是**装饰**，路线和箭头是本职：
少了这层，`map.js` 里一个异常就会让**同一帧的 `NAV_UPDATE` 也发不出去**
（症状是"Overpass 一挂，设备连箭头都不动了"）。

### 必须改的（环境差异）

- **传输**：串口 → BLE。分片大小要**试探**（页面拿不到协商后的 ATT MTU，
  见 `docs/ble.md` 第 2 节）：`512 → 244 → 185 → 128 → 64 → 20`。
  写失败时**作废整帧重发**，绝不续传 —— 续传会拼出一帧 CRC 永远不对的数据。
- **发送队列**：一帧 1.4KB 的 `NAV_MAP` 在 MTU 23 时是 78 次写。同步做完会把
  10Hz 循环卡死。所以是"有界队列 + 异步 drain，每帧让出一次事件循环"，
  队满时丢**最旧的 `NAV_UPDATE`**（下一帧 100ms 后就到），**绝不丢 `NAV_ROUTE`**。
- **位置源**：NMEA 串口 → `navigator.geolocation.watchPosition`。航向策略沿用
  PC 版：速度 < 2 m/s 时 GPS 对地航向不可信，**沿用上一次的有效航向**。
- **缓存**：磁盘 JSON → `localStorage`（配额爆了就丢一半再写，失败也不影响导航）。
- **抓取不阻塞**：PC 版用后台线程，这里靠 `fetch` 的异步性 ——
  `refresh()` **绝不 await**。

### 从对拍里抓出来的两个真 bug（都已修，并被测试钉住）

1. **Python 的 `round()` 是银行家舍入**（`.5` 取偶），JS 的 `Math.round()`
   是四舍五入。9 处 `int(round(x))` 都会在正好 `.5` 上差 1。
   → `navmath.pyround()`。
2. **`navigator.py` 是两种取整混着用的**：角度类字段 `int(round(x))`，
   距离/速度/ETA/进度 `int(x)`（**截断**）。
   → 前者 `navmath.pyround()`，后者 `navmath.pyint()`。混错一个就是
   "距离差 1 米、进度差 1%"这类看着像显示差异、实际是**字节不同**的 bug。

`phone/test/parity.mjs` 的 4b 节会**直接读 `app.js` 的源码**核对这 11 个字段
各自用了哪个取整函数，防止测试与实现各改一半、结果测试自己通过。

## 5. 已知的坑与未验证项

### 协议里一个**已经存在**的坑（Python 也一样，不是移植引入的）

`MAX_MAP_TOTAL_POINTS = 400` 是**接收端数组容量**，但它比一帧能装下的还大：
`NAV_MAP` 的 payload = `4 + seg_count + 4*total_pts`，而 `MAX_PAYLOAD = 1536`。

- `400 点 + 64 段` → 1668 字节 → `encode_frame()` **直接抛错**
- 真正可发的上限：`4 + seg_count + 4*total_pts ≤ 1536`
  （64 段时最多 367 点；60 段时最多 368 点）

所以手机端靠**生成端**的 `MAP_MAX_POINTS = 330` / `MAP_MAX_SEGMENTS = 60`
（60/330 → 1384 字节）压住，并额外提供了
`proto.nav_map_fits()` / `nav_map_max_points_for_segs()` 在运行时复核。
`app.js` 里底图帧的编码包了 try/catch —— 哪怕它超了，也只是**丢一次底图**，
不会把这一轮的 `NAV_UPDATE` 一起带崩。

顺带一个推论：`NavMap.pack()` 里那段"装不下的段整条丢掉"的分支，
**在编码到 wire 时永远走不到**（要丢段就得越过 400 点，而 400 点已经超
`MAX_PAYLOAD`）。它是防御性代码，只在直接调 `pack()` 时生效。
`selftest.mjs` 把这个事实钉住了。

### 没有验证的（没有手机、没有设备，无法端到端）

- **实际协商出来的 ATT MTU**，以及 512 分片到底能不能用。设备侧对切分点不敏感，
  所以最坏情况是"退到 20，慢但正确"。
  > ⚠️ **v12 更新（真机已确认一半）**：APK（原生路径）这边**不能再按 `MTU − 3` 分片** ——
  > 真机 MTU 517 时 `517 − 3 = 514` 会被 Android 框架的硬上限 **512** 拒掉，
  > 而且那条异常是**同步抛在插件线程上**的（JS 接不住 ⇒ 进程直接死，dropbox 里有完整栈）。
  > 所以 `ble_native.js` 现在的上界是 `min(MTU − 3, 512)`，并且**从 20 字节起步**、
  > 只在连续成功之后才升一档（学到的值跨启动落盘）。上面的
  > `512 → 244 → … → 20` 那条阶梯是 **PWA（Web Bluetooth）** 那条路的，
  > `ble.js` 一个字节都没改。详见 `docs/android.md` 第 9 节。
  > "512 分片到底能不能用"现在由自测回答了一半：**发出去的每一片都不会超过 512**
  > （`phone/test/native.cjs` 第 15 节的模糊测试），另一半（这块板子/这台手机能吃到多大）
  > 由 App 里的自适应升档在真机上自己试，读数在「选项 → 高级 / BLE 分片」。
- **真机吞吐**。`docs/ble.md` 第 3 节的表是估算。1.4KB 的底图在 MTU 23 下
  约 3 秒 —— 如果实测这么慢，先看页面 `已发/丢弃`，必要时把
  `map.js` 的 `max_points` 调小。
- **后台限流**。`setInterval` 在页面切后台后会被浏览器压到 ~1Hz（Chrome 实测
  1000ms 一跳），设备收到的帧率跟着掉 —— 这一版**没有**假装解决它，而是做了
  两件能做的事（都在 `app.js`）：
  1. **屏幕常亮**（Screen Wake Lock，`ScreenWakeLock` 类）：导航开始时
     `wakeLock.request('screen')`，停止导航时 `release()`；页面被隐藏时浏览器
     一定会把锁收走，所以 `visibilitychange` 回到前台会**重新申请**
     （漏掉这一步 = 用户切出去看一眼消息，回来屏幕就再也不常亮了，而界面上
     看不出来）。没有这个 API、或者申请被拒（低电量等）都只写一行日志，
     **绝不影响导航**。状态面板的 `屏幕常亮` 那一格直接写：`已保持 / 空闲 /
     已释放 / 不支持 / 失败`。
  2. **把症状说出来**：循环周期超过 `LOOP_SLOW_MS = 400ms`（10Hz 的 4 倍，
     后台节流的 1000ms 是它的 2.5 倍）就在状态面板的 `循环` 那一格写
     **"页面在后台，帧率已降"**，并在日志里写一行 `[loop] 帧率已降…`；
     周期回到正常时再写一行"已恢复 10Hz"（帧计数一直没停）。用户因此知道
     这是浏览器行为，而不是导航坏了。
  ⚠️ 两条都**没有**在真机/真浏览器里复验过（Node 自测只能钉住"接线"）：
  锁到底拿没拿到、切后台到底掉到多少 Hz，只有上了车才知道。彻底的正解仍然是
  把导航循环挪进 Web Worker 或者原生前台服务（BLE 在 Worker 里不可用，需要
  postMessage 转一层）—— 这一版没做。
- **GPS 航向质量**。手机固定在车上时 `coords.heading` 够不够稳、低速时
  "沿用上一次航向"够不够，只有真机能回答。**这是整个方案最大的风险点**：
  设备没有磁力计，方向完全依赖手机 —— 手机一歪，全屏就歪。
- **Overpass / OSRM 的实际可用性**。两者都是公共实例，会限流。代码有缓存和
  退避，但没在真机路线上跑过。
- **Overpass 镜像：只有 `maps.mail.ru` 是开发机上实测过能用的**（`map.js` 的
  `ENDPOINTS`）。9 个候选里它是唯一 `/api/status` 回 200、真查询也回 200 的
  （17.6 秒，带 `Access-Control-Allow-Origin: *`），它也是 rOpenSci 的 `osmdata`
  包 `list_overpass_urls()` 默认采样的公共实例之一。另外两个
  （`overpass-api.de`、`overpass.kumi.systems`）是 Python 版就有的 fallback，
  **一次都没连通过**。
  ⚠️ 而且这份实测是**开发机**上的，**没有**在手机所处的网络、也没有在真正的浏览器里
  复验过（手机在另一个网络）。换/加镜像时请自己确认三件事：探活、真查询、CORS 响应头
  —— "写在列表里"不等于"能用"。
  好在 `map.js` 现在会**记住上次成功的那个镜像**（sticky，`navpuck.osm_endpoint.v1`），
  所以"哪个活着"这件事不用靠维护这份静态列表来猜。
- **PWA 安装与离线**。manifest / service worker 只做了语法与清单检查，
  没有在真机上装过。

### 首次真机联调最可能需要调的

| 症状 | 先看哪 |
|---|---|
| 完全没反应、按钮点了没弹框 | 是不是 HTTPS/安全上下文？页面顶部有没有红色"不支持 Web Bluetooth"提示 |

| 箭头方向乱 | **手机和车头是不是同向固定**；选项里那个勾选状态 |

## 6. 改了协议相关代码之后必须做的

`proto.js` / `navmath.js` 的任何改动，都要：

```bash
node phone/test/run-all.mjs       # 四套全跑，必须全绿
python tools/selftest.py          # PC/C++ 侧没被搞坏，必须 50/50
```

黄金向量（`test/navcore_vectors.json`）由 Python 侧生成，是**四方**的公共真相：
C++ 固件、Python PC 端、JS 手机端、以及 `docs/protocol.md` 里那段十六进制。
要重新生成：

```bash
python tools/navpuck_proto.py --emit-vectors test/navcore_vectors.json
python tools/navpuck_proto.py --selfcheck
python tools/selftest.py
```

### 改了 `phone/` 里任何一个**被预缓存的文件**之后

`sw.js` 的 `ASSETS` 清单里那些文件（`index.html` / `style.css` / `app.js` /
`map.js` / `ble.js` / `route.js` / `proto.js` / `navmath.js` / `manifest.webmanifest`
/ `icon.svg`）改完，**必须**把 `sw.js` 顶部的 `CACHE` 版本号 +1
（当前是 `navpuck-phone-v4`）。Service Worker 是**缓存优先**的：版本号不变，
手机上的 PWA 会一直吃旧副本，症状是"代码明明改了、手机上还是老样子"——
而且因为改动本身没生效，用户根本看不出是缓存问题。

这一版（`v3` → `v4`）改的正是底图那套（`map.js` 的镜像顺序 / 超时 / sticky +
本文件），所以**必须在手机上看到 `v4` 才会拿到这个修复**。
